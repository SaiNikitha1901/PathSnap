PathSnap: Viva Guide

UE24CS352A ML Hackathon · Team guide · Batch 1 (EDA + models) first, then Batch 2 (Bayesian, HMM, API, UI)
The problem in one line: GPS points from a car are noisy (they jump around by 5–40 m). We must find which road segment (arc) the car was really on at every GPS point, and then join these into a connected route. This is called map matching.

  • Partitions: 80 train trips, 10 student-test trips, 10 evaluator trips (hidden, used only on the final day).
  • Size: about 208,000 GPS points in train and about 19,000 in student-test. Road networks differ a lot per trip: from about 1,000 nodes up to 88,000 nodes, and up to about 300,000 arcs.
  • Worldwide: trips are in many different places (different UTM zones), not only one city.
  • Time gaps: most steps are exactly 1 s. A few are 2–16 s (GPS dropouts).
  • Key surprise: the route is a list of arcs, not one label per GPS point. Example: trip 1 has 1,315 GPS points but only 525 route arcs. Some short arcs have no GPS point on them at all. So we had to create a label for each point ourselves (Section 3).
  • "A row in the GPS file does not correspond to a row in the road file". The PDF warns about this, and this is exactly why.

2. Preprocessing

Q: How did you clean the data?
We removed rows that are not numbers or have impossible coordinates (|lon| > 180, |lat| > 90). We sorted by time and dropped duplicate timestamps. We report how many rows each step removed (the missing-value analysis).
Q: Why not use plain distance in degrees?
Longitude and latitude are angles, not metres. One degree of longitude gets shorter as you move away from the equator. So we project to UTM (a flat map in metres). We pick the UTM zone from each trip's own longitude (zone = floor((lon+180)/6)+1). After that, normal Euclidean distance is in real metres.
Q: Which partition was used for EDA?
Train for the statistics and model fitting. Student-test only for comparing models. We never touched the evaluator trips.

3. Making a label for every GPS point (our own idea)

Q: The route has no per-point labels. How did you get them?
We used monotonic alignment with dynamic programming. The car drives the route in order, so point 1 must be on an earlier (or the same) route arc than point 2, and so on. Among all assignments that never go backwards, we choose the one that gives the smallest total distance from the points to their arcs. Each point's distance is capped at 100 m, so one crazy GPS jump cannot spoil the alignment.
DP rule: cost[i][k] = dist(point i, route arc k) + min over k' ≤ k of cost[i-1][k']. Then we back-track.
Q: Is that label perfect?
No. It is derived reference, not physical truth. The median distance from a point to its label arc is about 4.5 m, the 95th percentile is about 16 m, and the 99th percentile is about 37 m. A few trips have points 100+ m away, where the route itself may be imperfect. We say this openly.

4. Candidate generation

Q: What is a candidate?
For each GPS point we take all arcs within R = 50 m, and keep at most the K = 10 nearest. We find them fast with a spatial index (shapely STRtree), so we never check every arc. Each (point, candidate arc) pair is one row for the classifier.
Q: Why 50 m and 10?
From the train data: about 99% of points are within 37 m of their reference arc. With K = 8 the miss rate was already under 1% on most trips, so 50 m / 10 has a small safety margin. Bigger values mean more rows and slower code, for almost no gain.
Q: What is Candidate Miss Rate?
The % of GPS points whose true arc is not in their candidate list. No model can get those points right, so it is the ceiling on accuracy.

5. Features (why each one)

FeatureWhy it helps
dist, dist_rank, dist_minus_min, dist_ratioA closer road is more likely. Comparing against the nearest candidate makes the feature fair across noisy and clean trips.
heading_diff, cos_heading, heading_validThe car's direction (from neighbouring points) vs the arc's direction. This is the only way to tell A→B from B→A, because they lie in the same place. If the car is almost stopped (< 3 m movement), the direction is unreliable, so we flag it.
win_dist, win_dist_minus_minThe mean distance of the 5 nearby points (i−2..i+2) to the arc. A parallel street can be close to one noisy point, but not to the whole window.
proj_t, arc_lenWhere along the arc the point falls (0 = start, 1 = end), and the arc length.
from_out_deg, to_out_degJunction size (how many roads leave each end).
speed, dt_prevFast speed suggests a main road. A big dt means a GPS gap.
near_prev_best, near_next_bestIs this arc the same as, or connected to, the nearest arc of the previous/next point? This gives continuity information.
n_candsA dense area (many roads) makes matching harder.
Q: Any leakage?
No. No feature uses the route file. The route is used only to make the training label and to score results. Every feature can be computed for a brand-new trip.

6. The ML task and metrics

  • Task: binary classification. "Is this candidate arc the true arc for this point?" (1/0). Then for each point we pick the candidate with the highest probability. That is Top-1.
  • Imbalance: only about 1 in 10 rows is positive, so we use class weights and macro F1 (the average of the F1 for class 0 and class 1). Plain accuracy would look high even for a model that always says "no".
  • Observation Top-1 accuracy (our primary metric): % of GPS points where the top candidate equals the reference arc. This is what map matching really cares about.
  • Log loss: measures how good the probabilities are. It matters because the HMM uses these probabilities.
  • Route continuity: % of consecutive predictions that are the same arc or connected within 3 arcs in the driving direction.
  • Validation: GroupKFold (5 folds) grouped by trip. Points from the same trip are very similar, so a normal random split would leak and give over-optimistic scores.

7. The models we compared (≥ 5, different families)

ModelFamilyWhy try it / what to say
Logistic RegressionLinearSimple baseline with good probabilities. Limit: only a linear boundary, so it cannot learn "close and same direction" well. Features are scaled.
Gaussian Naive BayesProbabilisticVery fast. It assumes features are independent, but dist and win_dist are strongly linked, so its probabilities are over-confident (worse log loss).
KNN (distance-weighted)Instance-basedLabels a row by its most similar rows. Needs scaling. Slow at prediction time on many rows, so we trained it on a sample.
Random Forest / Extra TreesEnsemble (bagging)Many trees on random subsets. Learns non-linear rules and is stable. Can overfit if trees are deep (watch the train vs CV gap).
HistGradientBoosting / LightGBMBoostingTrees added one after another, each fixing the previous errors. Usually the best on tabular data, fast, and gives good probabilities. Our final choice (Section 0).
MLP (neural net)NeuralHidden layers learn non-linear combinations. Needs scaling. Has a real loss curve (loss_curve_), so we plot it. Do not draw loss curves for models that have none.
Q: How did you pick the final model?
The highest student-test Top-1 accuracy, together with good log loss (because the HMM needs good probabilities), a stable CV score across folds, and fast inference. We did not pick it by training accuracy.
Q: Overfitting?
Compare train score vs CV score vs student-test score. A big gap means overfitting (deep trees, KNN with small k). All three being low means underfitting (Naive Bayes, Logistic Regression).
Numbers: see Section 0. LightGBM is the best on Top-1 (0.903 on student-test). Naive Bayes is the worst (0.853, log loss 0.708).

8. Batch 2 basics (learn after Batch 1)

Q: Bayesian hyperparameter optimisation?
We use Optuna's TPE. Unlike grid or random search, it learns from past trials which areas of the search space look good, and tries there next. Same GroupKFold, objective = CV Top-1 accuracy, about 40 trials. We report tuned vs untuned.
Q: Why an HMM at all?
The classifier looks at each point alone, so two neighbouring points can land on roads that are not even connected. The HMM adds road connectivity over time.
  • Hidden states: the candidate arcs of each point. Observations: the GPS points.
  • Emission: the classifier probability (normalised over that point's candidates), to a power α, with a small floor ε.
  • Transition: exp(−|driving distance − straight distance| / β). If the road distance between two candidates is about the same as the GPS jump, the move is likely. A huge detour is unlikely. The driving distance comes from Dijkstra on the directed road graph.
  • Unreachable pair: a big fixed penalty, not zero, so the chain never breaks. Large GPS gap: β grows with the gap, and after 60 s the chain restarts. Point with no candidate: skipped, and its gap is filled with the shortest path.
  • Viterbi: dynamic programming. δ_t(b) = max_a [δ_{t−1}(a) + log T(a,b)] + log E_t(b). Keep the best previous state for each state, then back-track from the end. Cost: O(T · K²).
  • Compare classifier-only vs classifier + HMM on pointwise accuracy, continuity and route F1.
Q: API and UI?
Laptop 1 (Nikitha's Mac) runs FastAPI with the model, the road data and the hidden labels. Laptop 2 runs an HTML page with a Leaflet map. The UI asks GET /trips for the list, then sends POST /predict {trip_id}. The server runs the full pipeline, scores it against the labels on the server, and returns only the predicted route and the metrics. The reference route is never sent to the UI. Every request is printed in the server terminal (the API logs).

9. Quick-fire questions

QuestionShort answer
Why directed arcs matter?Same road, two directions. Heading is the feature that separates them.
Why GroupKFold?Points from one trip are correlated, so splitting a trip across folds is leakage.
Why macro F1, not accuracy?Classes are about 1:9. Macro F1 gives the rare positive class equal weight.
Why log loss?It checks probability quality, and the HMM uses those probabilities.
What limits the best possible accuracy?The candidate miss rate, plus label noise from the alignment.
Clustering?Not used as a classifier. Cluster ids are not labels without a mapping.
Where are the evaluator trips?Only on the server, only at final evaluation, never used for training or tuning.
Why UTM?It gives metres, so Euclidean distance is valid at city scale.
Why STRtree?A spatial index finds nearby arcs without checking all 300k arcs.
Hardcoding?None. Every prediction is computed live from the raw files through the API.
